# 已放弃：Claude Chat Organizer（姊妹产品）

> **状态：2026-08-13 放弃，代码已删除。**
> 本文件取代原 `docs/prd/claude-chat-organizer.md`（已删）。保留它的唯一目的：
> 记住我们在这个方向上踩过什么坑，别再走一遍。

## 原本要做什么

一个**独立上架**的 Chrome 扩展，给 claude.ai 加四件事：文件夹、跨会话正文全文搜索、置顶、干净的 Markdown 导出。100% 客户端、零后端、复用用户自己的登录态；与 persona-chat 共享代码底座但单独上架、双向交叉推广。

做到了什么程度：**代码写完并验证通过**——3078 行，`tsc` / `pnpm build` 干净，23 项纯逻辑断言 + 11 项真实数据核心链路断言 + 9 项真机 UI 断言全过。不是做不出来，是做出来之后判断它不值得上架和长期维护。

## 为什么放弃（按分量排序）

### 1. 四个卖点里有两个和 Claude 原生功能重叠

开发期探接口时才发现，会话对象上本来就带：

- **`is_starred`** —— Claude 原生星标，就是置顶。我们的"置顶"是它的影子实现，甚至专门写了"只读同步、绝不写回"的逻辑去伺候它。
- **`project_uuid` / `project`** —— Projects。不完全等于文件夹（它绑上下文、且要在建会话时就选），但对"我想把会话归归类"这个诉求，原生已经覆盖了相当一部分。

剩下真正站得住的只有**全文搜索**和**干净导出**，而全文搜索这条已被 AI Toolbox（30k 装机、跨平台）占住。

> **教训（可迁移）**：评估任何"给 X 平台加个功能"的点子时，**先把该平台的内部接口字段列一遍**。字段表是它已有功能的诚实清单，比看 UI 更快、更全——UI 藏得住的功能，字段藏不住。这一条如果在 PRD 阶段做，能省掉整轮开发。

### 2. 商业模式是死结，不是排期问题

v1 定的是"全免费 + 导流 persona-chat"。但 persona-chat 自己也是免费的——**免费产品导流给免费产品，漏斗末端是空的**。

买断被推迟到 v2，理由是接支付会引入第三方网络请求、破坏"零外发"的隐私叙事。但这个理由在 v2 同样成立。所以这不是"以后再说"，是一个结构性矛盾：**这个产品的核心卖点（零外发）和它的收费方式互斥**。

### 3. 无文档接口要长期交维护税

整个产品架在 claude.ai 未公开的内部接口上。本轮就踩到 `m.text` 恒空这种静默陷阱（详见下）。Anthropic 改一次字段，产品就静默坏掉——用户不会来提 issue，会直接给一星。**收入为 0 的产品，交不起这笔长期税。**

## 一个没验就放弃的事实（如果将来重启，从这里开始）

整个产品压在一句话上：**"Claude 原生搜索只搜标题"**。这是 PRD 调研期（2026-08-12）的结论，放弃时**没有重新验证**。

将来若重新评估任何 Claude 工具类方向，这条要先验：登录后搜一个**只在正文里出现、标题里没有**的词。如果 Claude 已经补上正文搜索，方向当场归零。

## 技术上学到的、跨项目有用的东西

已全部进 memory，这里只留索引：

1. **claude.ai 内部接口三个静默陷阱**——`chat_messages[].text` 恒为空字符串（正文在 `content[]` 的 `type:"text"` 块里，照 `m.text` 建索引会得到一个语法正确但完全为空的索引，无任何报错）；`/api/organizations` 返回**多个** org 且会话列表是 per-org 的（取 `orgs[0]` 会整块漏数据）；分页 `?limit&offset` 生效但响应是裸数组，**终止条件必须是"返回空数组"**而非"条数 < limit"。
2. **Chrome for Testing 测试环境**——常规 Chrome 151+ 已彻底移除 `--load-extension`。改用 CFT：独立 app + 独立 profile + 独立端口，**与日常浏览器并行，测试不必关掉工作浏览器**。已抽成 `.claude/skills/pc-test/scripts/launch-cft.sh`，persona-chat 通用。
3. **验"存储真的往返了"要关掉面板再打开**——只看点击后的即时 UI，分不清 React 内存态和 `chrome.storage`。
4. **不依赖 `chrome.*` 的模块可以直接注入页面上下文验**——把 API client / IndexedDB 层 / 搜索层用 esbuild 打成 IIFE，CDP 注入后对真实登录态跑断言，比装扩展快得多。

## 流程上值得改的一条

PRD 阶段的 Compatibility Checklist 只检查了"**我们能不能做**"（成本/权限/过审/架构），没有一栏检查"**平台是不是已经做了**"和"**做出来靠什么赚钱**"。这两个漏洞正好对应上面的放弃理由 1 和 2。

→ **下次写 PRD 时，Checklist 应加两栏：**
> - **原生重叠**：目标平台的接口字段/设置项里，是否已有等价功能？（列字段表，不看 UI）
> - **收入路径**：v1 的钱从哪来？如果是"导流"，导到的那个东西自己怎么赚钱？
